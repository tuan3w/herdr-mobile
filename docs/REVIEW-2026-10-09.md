the Android shell, at commit `4555860` (0.1.5) plus the uncommitted gallery and
tab-bar work (a tab swipe that existed then has since been removed; no finding

## How to read this

- These are **reviewer claims, not facts**. Nothing was built, run or tested
  except where a finding says "repro". Each finding has a confidence (0-1);
  below ~0.5 treat it as a lead.
- Verified by the person who merged the reports (read the code or ran a
  throwaway reproduction): marked **VERIFIED**.
- Phone numbers (frame stalls, battery) were not measured. Desktop-VM numbers
  are marked as such.
- Priority: P1 critical (silent approval, data loss, security, freeze),
  P2 user-visible wrong behaviour or likely leak, P3 medium/low or
  maintainability. Security findings use severity words instead.
- **Re-verified and fixed, 2026-10-09.** Six verifiers re-checked all 20 P1
  findings and 11 P2/P3 ones against the code (a reproduction where they
  could), and the confirmed ones were fixed with regression tests. The next
  section says what held, what was corrected and what is still open. Where a
  finding further down disagrees with it, the next section wins; the findings
  below are left as the reviewers wrote them.
- Delete this file once the findings are fixed or rejected. It is a work list,
  not a design document (see "Writing things down" in `AGENTS.md`).

## Round 1: agent session repositories
#### P1 (conf 0.55) Observed approvals drop the detector's second-tap/hold reason (cut command can be allowed in one tap)
`app/lib/data/repositories/observed_requests.dart:184-208`

`promptRequest` builds `PermissionOption(optionId, name, kind)` from each `QuickReply` and discards `needsConfirm`/`risk`. In `prompt_detector.dart` those flags are set from the WHOLE subject (`cutRisk: longCommand` when the subject is cut at 6 rows x 160 chars, scope risk from the question and the row above, risk from the option's own text). The chat dock only re-derives risk from the subject it shows (`describePermission`/`optionGate`), which for observed prompts is the already-truncated subject or the log call's input. Scenario: omp or a pane shows a long command whose dangerous tail is cut with an ellipsis. Terminal chips (`reply_chips.dart`) require a hold or second tap, but the chat dock's Allow is a single tap because the risk judged on the visible text is null. This breaks 'a hold for what is risky' and 'the person sees what they approve'. Fix: carry `needsConfirm`/`risk` into `PermissionOption` (or a request-level risk) and have `optionGate` honour it.

#### P1 (conf 0.45) Command shown for an observed approval comes from a guessed open tool call, not the prompt on screen
`app/lib/data/repositories/observed_session.dart:966-1015`

`_syncPending` builds the request with `promptRequest(prompt, call: _openCall())`. `_openCall()` returns the LATEST log tool call with no result, and its comment says 'most likely'. When `call != null`, `promptRequest` uses the call's `rawInput` and title and ignores the on-screen `prompt.subject`. The freshness check in `_answerPermission` compares only `promptSignature` (question, subject, labels) of the screen, so the displayed command is never checked against the screen. With parallel or overlapping tool calls (several open calls, the pane asking about an earlier one), the person sees command B and the risk badge computed on B, but the keys approve the screen's command A. Fix: always show the screen's subject, and use the call's input only when it matches the subject (for example, the command string is contained in the screen text); otherwise fall back to the subject.

#### P2 (conf 0.85) ObservedAgentSession leaks machine/parent listeners on every acquire/release cycle
`app/lib/data/repositories/observed_session.dart:553-575`

`acquire()` adds `_onMachine` to `machine` (and `parent`) when `_holds == 1`, but `release()` never removes it; `dispose()` removes it exactly once. Each open, close, reopen of the same session adds another identical listener (ChangeNotifier allows duplicates). While unheld, the session keeps running `_onMachine`/`_refresh` on every machine notification (pane status churn), which costs battery. After `dispose()` (the registry drops it after `idleAfter`), N-1 listeners remain on the long-lived `MachineConnection`, so the whole disposed session (its `_log` transcript and mapper) is retained. Fix: add the listeners on the 0->1 transition and remove them when `_holds` drops to 0, or guard with a flag; `dispose` must then only remove if added.

#### P2 (conf 0.5) Prompt lost silently when the link drops after the optimistic turn start
`app/lib/data/repositories/acp_agent_session.dart:1394-1450`

`_promptNow` computes `started` from the client's optimistic state (the user row and `turnActive` are set synchronously inside `client.prompt`) and then returns `true` at once. If the RPC later fails with `JsonRpcClosedException` (link died before the agent got it), the `catch` skips the hold branch because `started` is true, and `_guard` swallows the error because `!_ready` ('already said by link'). The message row stays in the transcript as if sent, the composer was already cleared, and nothing is queued or flagged. After re-attach, `withHeld` keeps the local row, so a prompt the keeper never saw looks delivered forever. The same applies to agent-side rejections after local start (for example Codex 'does not support image input'): the text and image are gone from the composer and are not held, although `_words` suggests 'Send it without the picture'. Fix: on a closed-link or rejected prompt where the turn did not actually run, hold a copy in the queue with a reason, or mark the row as unconfirmed.

#### P2 (conf 0.55) _afterDrop updates the keeper listing without notifying, and hides later changes from update()
`app/lib/data/repositories/acp_agent_session.dart:1026-1050`

After a drop, `_afterDrop` does `_info = mine; _carried = null; _syncPhase();` and never calls `_changed()`. `phase` is derived from `_info`/`_carried`, so it can flip (for example working -> blockedOnPermission because the keeper now has `pending > 0`) with no notification. Worse, the repository's next listing calls `update(next)`, which diffs against `_info` that is already overwritten, so `before.pending != next.pending` is false and no `_changed()` fires there either. Listeners (board, repository signature, alerts) only learn when a later link change happens: a successful attach, or `failed` after up to 12 back-off tries. A session that started waiting for the person during an outage can stay shown as working or idle for minutes, against 'Does anything need me?'. Fix: compare old and new `_info` in `_afterDrop` and call `_changed()`, or route the list result through `update`.

#### P2 (conf 0.4) Dismissing an observed permission/question sends blind `esc` without re-reading the pane
`app/lib/data/repositories/observed_session.dart:1183-1210`

For `PermissionSelected` the code re-reads the pane and checks `promptSignature` before sending keys. For `PermissionCancelled` (the dock's dismiss) it calls `machine.api.sendKeys(paneId, ['esc'])` with no read; `answerQuestion` for any non-accept response does the same via `_keys(['esc'])`. If the terminal moved on between the last preview and the tap (answered at the desk, or the prompt timed out), the `esc` goes to a working agent and interrupts the turn, or opens omp's message tree, which the code itself says a double esc does. The 'The terminal changed before that answer was sent' protection is skipped on exactly the path with the least intent. Fix: re-read and compare the signature before the esc, like the Selected path.

#### P3 (conf 0.4) Held sessions bypass retry back-off on every repository rebalance
`app/lib/data/repositories/acp_agent_session.dart:670-685`

`_wantChanged` only leaves a retry alone when `_holds == 0` (`if (retrying && _holds == 0) return;`). The repository calls `want(true)` for every held session on each `_rebalance`: every board listing (30 s), every other session's signature change, and every `acquire`/`release`/`warm`. For a screen-held session in an outage, each nudge cancels the pending back-off timer (`_doAttach` calls `_cancelRetry`) and attaches again at once. `_attempt` only grows in `_scheduleRetry`, so `maxAttempts` is never reached and the session never becomes `failed`/'Retry'. The comment justifies the bypass for a person opening the screen (`acquire`), not for the repository's nudges. Result: radio and battery cost and a retry loop with no classification on a flaky link. Fix: bypass the back-off only from `acquire`/`reattach`, not from `want`.

#### P3 (conf 0.4) Queued messages stay 'waiting' across failed/ended/evicted links and auto-send on later reattach
`app/lib/data/repositories/acp_agent_session.dart:1292-1310`

`sendBlocks` queues messages while `_waitsForLink`. `_fail`, `_stop`, `_ended` and the evicted path never hold or flag the queue, so entries remain `QueuedState.waiting` indefinitely. When the person later taps Retry/`reattach()` (including 'Opened on another device' taking the session back), `_beginSettle` then `_pump()` sends the oldest entry as a prompt automatically, possibly hours later, or into a session another device is now steering, with no per-message confirmation. The Stop and error paths, by contrast, deliberately `holdAll`. Fix: `holdAll` with a reason ('Held because the connection was lost. Resume to send it.') when the link becomes failed/ended/evicted.

#### P3 (conf 0.4) Re-applying a partially applied log batch duplicates transcript rows after follow restart
`app/lib/data/repositories/observed_session.dart:762-790`

`_applyBatch` applies lines in slices with an await between them but only sets `_offset = batch.endOffset` after the whole batch. If the epoch changes mid-batch (`reattach()` -> `_restartFollow`, `_detach`, a background grace expiry during the large first tail batch), the loop returns with `_log` already containing the applied lines while `_offset` still has the old value. The next `_follow` resumes `from: _offset`, so those lines are delivered and appended again; `_resetLog` is not called. The transcript then shows duplicated messages and tool rows. Fix: on abandoning mid-batch, call `_resetLog()` (offset null), or advance `_offset` per applied slice.

#### P3 (conf 0.35) A throwing batch silently wedges the log follow while the link still reads live
`app/lib/data/repositories/observed_session.dart:724-765`

`_followOnce` chains batches as `work = work.then(...)`. If `_applyBatch`/`_applyLine` throws (any `_log.apply` reducer error; bad JSON is already caught by the mapper), `work` becomes an errored future. Every later `work.then(...)` is skipped, including the `onDone`/`onError` handlers, so `done` never completes, `_follow` hangs on `await _followOnce`, no retry or `_fail` happens, and the error surfaces only as an unhandled zone error. The `readyAfter` timer has already set `_logLink` to `live`, so a frozen transcript is shown as live (stale shown as live). Fix: wrap the apply in try/catch inside the chain and `done.completeError`, so the existing back-off or `_fail` classification applies.

#### P3 (conf 0.3) Repository disposes sessions still held by an open screen when a connection is rebuilt
`app/lib/data/repositories/agent_session_repository.dart:170-200`

`_apply` protects sessions that are `attached || held` from removal, but `_dropMachine(id, forget: false)`, used when `_onFleet` sees a new `MachineConnection` for the same profile (credentials changed), calls `_remove(s)` -> `s.dispose()` for every session regardless of `held`. A screen that holds one keeps a disposed `AcpAgentSession`. `_changed`/`_setProblem` are no-ops after dispose, so the screen shows the last state with no link change, and a send fails with 'Not connected' that is never displayed. Fix: keep the hold, or notify/close the screen (or re-adopt by key and swap), before disposing.

#### P3 (conf 0.4) Stale Stop flag can merge a queue after a turn the person never stopped
`app/lib/data/repositories/acp_agent_session.dart:1588-1600`

`cancel()` sets `_stopSendsQueue = true` whenever messages wait and `phase != idle` (this includes the listing's phase for an unattached session), and only afterwards returns when `_client == null || sid == null`. Nothing was cancelled, but the flag stays set; it is cleared only when a later turn starts after `!prev.turnActive`. If the attach then finds a turn already active, or the turn ends first, `_setState` treats the natural `endTurn` as 'stoppedByMe' and `mergeWaiting()` collapses the separate queued messages into one prompt instead of sending them one at a time. Fix: set the flag only after confirming `client != null` and the cancel was issued.

#### P3 (conf 0.6) Two near-identical god classes duplicate lifecycle, back-off, flush and helper code
`app/lib/data/repositories/observed_session.dart:848-925`

`AcpAgentSession` (about 1,950 lines) mixes link state machine, retry, queue dispatch, cache save/restore, background tasks, subagent logs, the `/rename` errand and notification coalescing. `ObservedAgentSession` (about 1,600 lines) adds pane key answering and the log follow. They copy the same logic instead of sharing it: `_changed`/flush coalescing with `_flushSlow`/`_quiet`, `background`/`foreground`/`keepAliveInBackground`/`_detach` grace handling, jittered back-off, `_words`, and a byte-identical `_folderName`. `_recordsEqual` hand-casts a 14-field record twice, so any added field must be edited in three places. Bugs like the listener leak and the epoch/offset issue above are the kind this duplication invites ('one of each'). Extract a shared notifier/lifecycle mixin and split queue, cache and background-work into collaborators.


## Round 1: ACP protocol, observed, decision, models
#### P1 (conf 0.72) Decode zipped replay as bytes, not per inflater chunk (UTF-8 corruption)
`app/lib/data/acp/zipped_lines.dart:32-45`

onInflated does `partial + utf8.decode(data, allowMalformed: true)` on every chunk that dart:io's zlib decoder hands to `_Collect.add`. That filter emits output in fixed-size buffers (~64 KB) that ignore UTF-8 boundaries, and a Z piece of a big thread inflates to far more than that. Any CJK, emoji or accented character straddling a chunk boundary becomes U+FFFD with no error (allowMalformed hides it). The corrupted text is shown and also stored by TranscriptRecorder in the cache. This hits exactly the big replays the feature exists for. Fix: accumulate bytes (BytesBuilder) and cut at 0x0A before decoding each whole line, or use `utf8.decoder.startChunkedConversion` and split the decoded stream into lines.

#### P1 (conf 0.8) stripAnsi silently deletes text after an unterminated OSC from judged paths and plans
`app/lib/data/decision/plain_text.dart:11-20`

`_osc = \x1B\][^\x07\x1B]*(?:\x07|\x1B\\)?` has an optional terminator, so `\x1B]` followed by anything but BEL or ESC removes everything to the end of the string. `_csi` likewise swallows the next visible letter after a malformed `\x1B[`. showHidden and plainLine call stripAnsi first, and permission_evidence runs showHidden on every path, plan and diff path. The doc promise is that the person reads what the machine would read. Scenario: an agent sends a location or path `/tmp/ok\x1B]0;/../../.ssh/authorized_keys`. The evidence card shows `/tmp/ok`, while the filesystem sees the full string. (The command subject on the card goes through visibleText, which does not strip, so it is not affected.) Fix: for judged text do not strip sequences; let isHiddenRune escape ESC as U+001B marker (0x1B is already hidden). Keep stripAnsi for tool output only, and require a terminator for OSC. Add an injection test with ESC ] plus a dangerous tail.

#### P1 (conf 0.85) commandRisk misses `bash -c "$(curl ...)"` and quoted/backslashed command words
`app/lib/data/repositories/command_risk.dart:57-125`

Three false negatives, reproduced against the same patterns (Python re, same semantics). (1) The downloaded-script rule only matches `curl|...sh`, `sh <(curl ...)` and `eval|source ... $(curl ...)`. `bash -c "$(curl -fsSL https://x/install.sh)"` and `sh -c "$(wget -qO- ...)"` give no reason, and neither does `curl ... | python3`. (2) `_start` is `(?:^|[\s;&|(`{])`, so a command word directly after a quote or backslash does not start a command. `\rm -rf /`, `"rm" -rf /`, `eval "rm -rf /"` and `docker exec c 'rm -rf /'` all return null from the `rm` rule. Only `sh -c '...'` is special-cased. (3) `kill -9 -1` is not matched, because the rule needs a digit right after the optional flag. Missing flags on a destructive command are the costly direction, since the hold-to-confirm guard only appears when a reason is returned. Fix: add quote and backslash characters to `_start` (a false positive costs one extra tap), add `(?:ba|z|da|k)?sh\s+-\w*c\s+["']?\$\(\s*(?:curl|wget)`, and widen the pipe-to-interpreter list (python*, node, perl, ruby). Cover each with a test.

## Round 1: connection, alerts, prompt detection
#### P1 (conf 0.5) Standing-grant check misses 'bypass permissions' and 'auto-accept edits' options
`app/lib/data/repositories/command_risk.dart:33-37`

`_standing` only matches "don't ask again", "always", "allow all", "this/the rest of the session" and "all edits". A terminal plan-approval menu such as `1. Yes, and bypass permissions` / `2. Fix: add `bypass\s+permissions`, `auto-?accept`, `accept\s+edits` (and similar mode switches) to `_standing`, and add corpus cases for them.

#### P2 (conf 0.5) Retry backoff resets after each successful snapshot, so a dying stream loops at 1 s
`app/lib/data/repositories/machine_connection.dart:466-486`

`_run` sets `attempt = 0` right after `_refresh()` succeeds and before `_watch()`. If the event stream ends or errors immediately after every connect (for example herdr rejects the `events.subscribe` set, or the server closes the channel), each loop does snapshot, subscribe, fail, `_set(reconnecting)`, then `_sleep(_retryDelay(attempt++))` with attempt=0 (1 s foreground, 30 s background). The backoff never grows, so the foreground radio is hit about once a second, and the link state flaps online/reconnecting with a listener notification each turn. Fix: reset `attempt` only after the stream has stayed live for some time (or delivered an event), not on snapshot success.

#### P2 (conf 0.4) Connect loop dies on any non-herdr exception and leaves the link stuck or stale as online
`app/lib/data/repositories/machine_connection.dart:458-500`

`_run` catches only `HerdrTransportException` and `HerdrApiException`. `HerdrApi.snapshot()` does `Snapshot.fromJson(r['snapshot'] as Map<String, dynamic>)`, and `_RefreshScheduler._run` forwards any refresh error to `end.completeError`. A TypeError or FormatException from an unexpected or newer herdr payload therefore escapes `_run` (an `unawaited` future, so it surfaces as an unhandled zone error). The `finally` clears `_looping` but nothing retries and the state is not updated. On first connect the machine stays `connecting` forever. If it happens from the scheduler while `online`, the state remains `online` with no poll or events, so stale data is shown as live. Fix: add a catch-all (`on Object`) that treats it as a non-fatal failure with the message and enters the backoff path.

#### P2 (conf 0.5) A flapping agent's announcement is dropped when its minute is up while the machine is out of reach (and can NPE)
`app/lib/data/repositories/attention_notifier.dart:435-444`

In `_follow`, the flap-window block clears `entry.value.due = null` first, then announces only `if (item.reachable)`. If the machine or session link is blipping at that moment, the track stays in `_tracks` with `posted == false` and no `due`. New episodes require `!_tracks.containsKey(key)`, so when the link returns and the agent is still blocked it is never announced: a silently missed alert, contradicting the class docs that a blip is the same episode. Also `byKey[entry.key]!` throws a null-check error when the track survived the 'ended' loop through `seen.unknown` (a session re-attaching: item absent, key unknown). #### P2 (conf 0.4) One exception in a reconcile permanently stops machine add/edit/remove for the whole fleet
`app/lib/data/repositories/fleet_repository.dart:192-194`

`_onMachinesChanged` chains `_reconciling = _reconciling.then((_) => _reconcile())`. `_reconcile` runs the connection factory, `c.start()` and `dispose()` for every machine, with no try/catch. If it throws once (a factory that throws for one bad profile, say), `_reconciling` becomes an errored future. Every later `.then` callback is skipped, so no machine can ever be added, edited or removed again until restart, and `settled()` returns an error. This breaks per-machine fault isolation: one machine can poison all of them. Fix: catch per machine inside `_reconcile`, and chain with `then((_) => _reconcile(), onError: ...)` or a catch-all.

#### P2 (conf 0.5) Foreground resume and pull-to-refresh swallow refresh failures, so a dead socket stays 'online'
`app/lib/data/repositories/fleet_repository.dart:229-239`

`retryAll` calls `c.refresh().catchError((Object _) {})` for online machines, and `MachineConnection.refresh()` is `_refresh()`, which on failure throws without touching the link state or the loop. `onForeground` relies on this when `_keepAlive` is on: its comment says 'a link that died meanwhile is found by that' refresh, but the error is discarded. `app/lib/data/repositories/prompt_detector.dart:318-331`

## Round 1: keeper script, SFTP, shell quoting
#### P1 (conf 0.85) Upload reports success when the last in-flight write fails
`app/lib/data/services/sftp_files.dart:664-712`

In `_pump`, a write failure is stored in `error`, but `error` is only checked at the top of a loop iteration. The loop condition is `offset < total || inflight > 0`. When the failing write is the last one outstanding (any file of 32 KB or less has exactly one write; for larger files, an ENOSPC or quota failure on the final block), the `whenComplete` handler drops `inflight` to 0 and wakes the loop. The loop then exits without rethrowing `error`. `_run` carries on to `remote.close()` and `_done.complete()`, so the caller is told the file is stored while the host holds an empty or truncated file. The agent is handed that path in the inbox `resource_link`. The upload tests only fail writes mid-stream (`dieAfterWrites`), where later writes are still in flight, so this case is not covered. Fix: after the `while` loop in `_pump`, add `if (error != null) Error.throwWithStackTrace(error!, errorTrace!);`. Add a test where only the last write fails.

#### P2 (conf 0.7) Alert redaction leaks `Authorization: Token <key>` and over-masks ordinary words
`app/lib/data/services/keeper_script.dart:400-418`

`redact_line` output goes to the user's `on-blocked` hook as `KEEPER_SUMMARY` and `KEEPER_TITLE`, described as safe to hand to a hook. `_BEARER` only covers `bearer|basic`. For `Authorization: Token 0123456789abcdef` or `token <key>` (GitHub and DRF style), `_SECRET_KV` takes the scheme word `Token` as the value. The key is left readable. Running the extracted function gave `Authorization: *** 0123456789abcdef`; the key is under 28 characters, so `_LONG` misses it. `curl -u admin:hunter2` and `mysql -p hunter2` also pass through unchanged. In the other direction, the bare `auth|token` alternation masks the next word of ordinary tool titles: `Edit auth.ts and add retry` becomes `Edit auth.ts *** add retry`. Fix: extend `_BEARER` to `bearer|basic|token|digest|negotiate`, or match `authorization\s*[:=]\s*(\w+\s+)?\S+` as a whole. Require a `=` or `:` separator for the generic key/value rule, so that a space-separated pair is not treated as a secret.

#### P2 (conf 0.8) Custom socket path is single-quoted, so the form's own `~/...` hint can never work
`app/lib/data/services/bridge_command.dart:381-385`

`buildBridgeCommand`, `buildMuxCommand` and `buildEventsCommand` all do `S=${_shQuote(socketPath)}`. The machine form's placeholder is `~/.config/herdr/herdr.sock` (machine_form_screen.dart:624) and the field has no validator. Typing that gives `S='~/.config/herdr/herdr.sock'`. The tilde is not expanded inside single quotes, so `[ ! -S "$S" ]` is true and the channel exits 78 with `no herdr socket at ~/...`. `keeperStartCommand` and `cdLine` do expand `~`, so the app handles `~` inconsistently across its shell helpers. docs/ENGINEERING.md says the path reaches the shell as a 'validated, single-quoted word', but nothing validates it. Fix: expand a leading `~/` as `"$HOME"/'rest'`, as `cdLine` does, or reject `~` in the form with a clear message.

#### P2 (conf 0.75) makeDirs hides the real mkdir error (permission denied shows as not found)
`app/lib/data/services/sftp_files.dart:264-274`

When `s.mkdir(dir)` fails (read-only or unwritable parent, quota, and so on), the catch block calls `s.stat(dir)`. The folder does not exist, so `stat` throws `SftpStatusError` code 2. That exception propagates from inside the catch and replaces the original error. The user sees 'No such file or directory' for `~/.herdr-mobile/inbox/...` when the real cause is permission denied. `reserve()` calls `makeDirs` on every first upload to a host, so this is the error shown when the home folder is not writable. Fix: wrap the follow-up `stat` in a `try`/`on SftpStatusError` and `rethrow` the original mkdir error when `stat` fails or the path is not a directory.

#### P2 (conf 0.5) Whole-operation timeouts on slow links tear down the shared SFTP session, including running uploads
`app/lib/data/services/sftp_files.dart:205-230`

`_run` applies `.timeout(metaTimeout=20s)` to a whole listing and `.timeout(readTimeout=60s)` to a whole read, whatever the progress. On `TimeoutException` it calls `_forget(session)`, which closes the one SFTP channel that uploads and browsing share. `list` resolves symlinks eagerly: batches of 24, each link doing `readlink` then `stat` one after the other, so about 2 round trips per link inside the 20 s budget. A folder with ~2000 symlinks (pnpm `node_modules`, `/usr/bin`, `.bin` folders) at 150 ms round trip needs about 25 s, so the listing fails with 'machine did not answer in time'. An 8 MB `read` (the default `readAll` piece, `remoteReadCap`) needs more than 140 KB/s to finish in 60 s. Each timeout closes the session and aborts every in-flight upload with 'connection lost'. Uploads already use a stall timeout (progress-based); browsing should too. Resolve links lazily or in bounded pages, and do not `_forget` the shared session on a timeout while other operations are running.

#### P2 (conf 0.4) A single malformed or deeply nested JSON line crashes the keeper and kills the agent
`app/lib/data/services/keeper_script.dart:1316-1326`

The main loop has no per-message exception isolation. `on_client_line` and `on_agent_line` catch only `ValueError` around `json.loads`. A line nested about 1000 levels deep raises `RecursionError` (a `RuntimeError`), which is not caught. The same applies to any unexpected exception in the `on_*` handlers or `log.add` (`dumps` on deep structures). The exception propagates out of `Keeper.run` to `daemon()`'s `except BaseException`, which SIGKILLs the agent's process group and marks the session 'The keeper crashed.'. The keeper exists so the agent outlives the phone link, yet one bad line from a client or the agent ends the session. The `follow` path already handles `RecursionError` (`follow_record`), so the keeper is inconsistent with it. Fix: catch `Exception` around each line dispatch in `readable`/`handle_agent_lines`, log it with `dlog`, and drop that line.

#### P2 (conf 0.5) Installer deletes the script file that herdr panes and resume commands point at
`app/lib/data/services/keeper_command.dart:88-96`

The installer unlinks every `keeper-*.py` except the new version. `Keeper.open_pane` types `python3 '<SCRIPT>' view ID` into a herdr pane. `View` also registers `resume = ["python3", SCRIPT, "view", kid]` with herdr via `report-agent -- RESUME_ARGV`. #### P3 (conf 0.35) Typed message that is only a number answers a permission request
`app/lib/data/services/keeper_script.dart:3253-3266`

In `View.on_line`, when exactly one permission is waiting and the text matches `^[0-9]{1,4}$`, it is sent as `selected` for that option. #### P3 (conf 0.45) Inbox cache of 'folder exists' goes stale and breaks every later upload until restart
`app/lib/data/repositories/host_inbox.dart:92-125`

#### P3 (conf 0.9) Three copies of the shell-quote helper
`app/lib/data/services/keeper_command.dart:35-35`

The same one-line quoter is defined three times: `quoteShell` in session_launcher.dart:4, `_shQuote` in bridge_command.dart:322 and `_shQuote` in keeper_command.dart:35. `key_generator.dart:165` inlines a fourth variant. #### P3 (conf 0.5) authorized_keys one-liner uses echo and can merge two keys into one line
`app/lib/data/services/key_generator.dart:163-168`

`authorizedKeysCommand` emits `echo '<line>' >> ~/.ssh/authorized_keys`. If the existing file does not end in a newline, the new key is appended to the last line of the previous key, which corrupts both. `echo` also interprets backslash escapes in some shells (dash, sh -c): a key comment containing `\n` or `\c` is altered or split across lines. #### P2 (conf 0.45) Live transcript keeps every tool call's rawInput/rawOutput/content (including base64 images) for the whole session
`app/lib/data/acp/session_state.dart:556-575`

`AgentSessionState.items` is never trimmed. `keepingNewest` is only applied to subagent log transcripts (`subagent_transcripts.dart:311`), and subagent children are capped at `SubagentRun.maxItems`. #### P3 (conf 0.45) A required form field of an unknown type (or an enum with no usable options) makes Accept impossible

#### P3 (conf 0.35) JSON-RPC response correlation: float ids are truncated onto other requests, and id:null errors leave a no-timeout prompt hanging
`app/lib/data/acp/json_rpc.dart:341-372`

`_response` maps `rawId is num ? rawId.toInt()` (`json_rpc.dart:435-440`), so a response with id `2.7` completes pending request 2. Repro with the copied file and requests 1 and 2 in flight: `{"id":2.7,"result":"for-b?"}` made request 2 complete with 'for-b?' while request 1 stayed pending. Separately, a spec error reply for an unparsable request, `{"id":null,"error":{"code":-32700,...}}`, hits `_dispatch` (`:363`), which requires `id != null`, and goes to `_problem('neither a request, a notification nor a response')`. Also, a peer request whose id is a float such as `1.0` (`:352-358`) is dropped with no reply, so the agent waits for it forever. Fix: accept only an int, or a string matching `^-?\d+$`, as a response id. When an error answer arrives with a null id, fail the oldest or all pending requests with that error (or at least surface it). Answer a malformed-id request with `-32600`.

#### P3 (conf 0.3) omp 'Backgrounded as job' text scan turns ordinary foreground output into a phantom running job
`app/lib/data/acp/background/omp_jobs.dart:57-64`

In `ompJobFacts`, every `execute` call whose `rawOutput.details.async` is null takes the fallback branch (`omp_jobs.dart:60-63`). #### P2 (conf 0.7) Connect bookkeeping ignores reset(): stale connects null the live client and leave orphan connections
`app/lib/data/services/ssh_transport.dart:191-198`

CONFIRMED round-1 item, with consequences round 1 did not list. In `_connected()` the `.catchError` handler does `_client = null` unconditionally, and the `.then` handler sets `_ready = c` and `_linkWatch` even after `_teardown` ran. `_drop(client)` (called from `client.done` via `ended()`) nulls `_client` whenever `_ready` is identical to the stale client. Interleaving (the normal network-change flow, `MachineConnection.reconnect()` = `reset()` then `start()`): A is connecting on the dead network. `_teardown` sets `_client = null`. The next request starts B on the new network. A then fails after its 15 s timeout, or succeeds and is closed by teardown, and either path sets `_client = null` while B is already installed. The next `_open` or `_connected()` finds `_client == null` and opens a third connection C, while B (still healthy) keeps its mux or events and is no longer reachable from `_client`. Effects: more than one SSH connection per machine (violating 'one connection per machine'), a second Tailscale check-mode sign-in link, and a leaked healthy connection that only its own watch can end. `_linkWatch` is also overwritten by the stale watch and then set to null by `ended()`, so `setBackground()` stops reconfiguring the live link watch. A dead link may then take 330 s instead of ~35 s to be found in the foreground, or the foreground 25 s ping keeps running in the background. Fix: capture the future in a local and guard every write: `if (identical(_client, mine)) _client = null`, only set `_ready` and start the watch if `identical(_client, mine) && !_closed`, and close the client otherwise. Also set `_ready` only from the epoch that started it.

#### P2 (conf 0.8) Non-terminal event-stream errors leave the SSH events channel open (leak toward sshd MaxSessions)
`app/lib/data/services/isolate_transport.dart:611-618`

CONFIRMED round-1 item, with the exact mechanism. In the worker the `sub` handler's `onError` runs `subscriptions.remove(id)` and sends `evtErr`, but never cancels the `transport.events(...)` subscription (`listen` has `cancelOnError: false`). On the main side `case 'evtErr'` removes `_streams[id]`, so when `MachineConnection` then cancels, `IsolateTransport.events` `onCancel` calls `cancel()`, finds `_streams.remove(id) == null` and never posts `cancel`. SshTransport.events emits many errors that do not close its stream: `out.addError(e)` for a bad ack (`unwrapResponse`), for a non-JSON line (`jsonDecode`), and `onError: out.addError` for `muxMessages`' 'event stream is corrupt'. After the corrupt-frame error `muxMessages` sets `broken = true` and stays silent, so the channel never ends on its own. The exec channel and its Python process then stay open until the whole SSH connection resets. The consumer resubscribes and opens another channel, so repeated errors exhaust `MaxSessions` (default 10, shared with the mux, SFTP and attaches), and other features then fail with 'Too many sessions'. The only isolate test ('a channel error reaches the listener, then the stream ends') covers a terminal error. Fix: in the worker's `onError`, cancel the subscription (`cancelOnError: true`, or `subscriptions.remove(id)?.cancel()`). In SshTransport.events, treat decode/ack errors as terminal by calling `fail(...)`, which closes the session.

#### P2 (conf 0.65) A login-shell banner or blank line breaks the events subscription and every bridge request
`app/lib/data/services/ssh_transport.dart:611-621`

CONFIRMED round-1 item. `events()` treats the first line on stdout as the `events.subscribe` ack: `if (!acked) { unwrapResponse(line); ... }`. `muxMessages` also emits blank lines as `''`. A banner (an unconditional `echo` in `.bashrc`, which bash sources for ssh exec) or an empty line throws `FormatException`, which becomes `HerdrTransportException('Malformed response ...')` via `out.addError`. The stream then ends in error, and with the leak above the channel stays open. The mux path (`muxReadyLine` wait, `_route` ignoring non-JSON) and the keeper path (`SshAgentHost._json`, `SshLogSource._onLine`: 'banner of a login shell, not ours') tolerate banners, so events are the odd one out. `_bridgeRequest` has the same flaw: `jsonLines(session.stdout).first` returns the banner, so `unwrapResponse` fails every request on hosts that use the bridge fallback. Fix: ignore lines that do not decode to a JSON object (or that lack `id`) until the ack arrives, and in the bridge take the first line that is a JSON object with the request id.

#### P2 (conf 0.5) A herdr that is slow to answer ping resets the whole SSH connection, including healthy keeper attaches
`app/lib/data/services/mux_client.dart:531-540`

CONFIRMED round-1 item (mux_client.dart heartbeat). `_beat` sends `ping` through the mux script to herdr's own socket (the Python script does not answer it locally). If no answer arrives within `_heartbeatTimeout` (5 s foreground, 15 s background), it dies as `MuxDeath.unresponsive`, and `SshTransport._startMux` then calls `reset()`. That tears down the SSH client and every channel: event streams, SFTP, uploads, and the keeper attach channels, which are separate healthy processes. Scenario: herdr is busy or stalled for over 5 s (a loaded machine, a big snapshot) while the link is fine. The result is a reset, a reconnect, a re-attach with a multi-MB replay, and the same stall again, which becomes a loop. The mux heartbeat counts only its own reply, whereas `LinkLiveness` explicitly counts any inbound byte for this reason. The SSH-level `LinkWatch` already detects a dead link, so the mux does not need to escalate. Fix: let the Python mux answer `ping` itself (a link and script liveness test that does not depend on herdr), or on `unresponsive` only close the mux and let the link watch decide; or do an SSH `client.ping` before `reset()`.

#### P2 (conf 0.7) SFTP open reports 'host does not allow SFTP' when the host is merely full or slow
`app/lib/data/services/ssh_transport.dart:425-430`

CONFIRMED round-1 item. `_openSftp` maps every `SSHChannelOpenError` to `_noSftp()` ('This host does not allow SFTP ... Enable the "sftp" subsystem in its sshd_config'). `channelRefusal` documents that codes 1 and 4 mean sshd's MaxSessions is exhausted, and `_open` handles them correctly, but this path does not use it. Result: Files shows a wrong, unactionable 'sshd_config' message, and a working host is blocked for 2 minutes after a single slow open. Fix: run channel-open errors through `channelRefusal` first (code 1/4 gives the 'too many sessions' text, not remembered). Remember 'no SFTP' only when the server answers the subsystem request with a failure, never on a timeout.

#### P3 (conf 0.65) Requests after reset() join a stale mux start and wait for the old connect
`app/lib/data/services/ssh_transport.dart:504-511`

CONFIRMED round-1 item. `_teardown` bumps `_epoch` and nulls `_mux` but not `_muxStart`. `_muxClient()` does `_muxStart ??= _startMux()...`, so a request made right after `reset()` joins the start that was in flight, which is already awaiting the old `_connected()` future (A). #### P3 (conf 0.55) Permanent connect failures are classified retryable and retried forever
`app/lib/data/services/ssh_transport.dart:302-317`

#### P3 (conf 0.55) TCP socket leaks when the private key cannot be read
`app/lib/data/services/ssh_transport.dart:220-241`

#### P3 (conf 0.4) Encrypted key is bcrypt-unlocked on the worker isolate on every reconnect
`app/lib/data/services/ssh_transport.dart:232-241`

NEW. `SSHKeyPair.fromPem(pem, passphrase)` runs in every `_connect`, inside the single worker isolate. The repo's own `KeyGenerator.readPublicKeyOffThread` documents that unlocking runs bcrypt and 'takes about a second on a phone'. #### P3 (conf 0.4) Retry and 'no SFTP' windows use the wall clock, so a clock jump disables the mux or Files for hours
`app/lib/data/services/ssh_transport.dart:503-509`

#### P3 (conf 0.3) Pin has no key type, so a server gaining a new host-key type looks like a changed key
`app/lib/data/services/ssh_transport.dart:274-283`

NEW. The pin is only the `SHA256:` fingerprint of whichever key dartssh2 negotiated; `onVerifyHostKey` receives `type` but ignores it, and the default host-key preference is `ed25519, rsa-sha512, rsa-sha256, ecdsa...`. Fix: pin a map of type to fingerprint (or pin the type and restrict `algorithms.hostkey` to it), and treat an unseen type as new, not changed.

#### P3 (conf 0.5) Events and bridge channels buffer all of stderr for the channel's lifetime

#### P2 (conf 0.6) Stop-by-message reports 'Asked to stop' without checking that the message went
`app/lib/data/repositories/acp_agent_session.dart:566-573`

`_stopByMessage` does `await send(message); return const BackgroundStopped(asked: true);`. `send` returns false for 'Not connected. #### P2 (conf 0.65) Batch message to agent sessions counts every target as sent without looking at the result
`app/lib/data/repositories/batch_actions.dart:112-112`

`BatchTarget.session` builds `message: (text) async => unawaited(session.send(text))`. `send` returns Future<bool>: false for 'Not connected' or a lost steer, and true when the text is only held in the queue after a refused prompt (`_promptNow` hold path). The doc comment above (`It never throws`) is true because `_guard` swallows the error, but the same guard means failure is only visible through the bool, which is discarded. The stated reason for not awaiting ('send returns when the turn is over') does not hold: `_promptNow` returns `Future.value(true)` as soon as the turn has started, and only waits for the turn when it has not started. Round 1's 'no per-target recheck' finding is about the plan; this one is about the outcome. #### P2 (conf 0.6) MachineRepository.remove mutates first and notifies last, so a failed write leaves the machine connected
`app/lib/data/repositories/machine_repository.dart:170-190`

`remove(id)` sets `_machines` to the filtered list, then awaits `_profiles.write`, then awaits `_secrets.delete(id)`, and calls `notifyListeners()` only at the end. If either await throws (a keystore error on `delete`, a prefs failure), the in-memory list has lost the machine but no listener is told. FleetRepository never reconciles, so the SSH connection to the machine the person just deleted keeps running and stays on the board. The private key stays in the keychain when `delete` was the step that failed. The only caller, machines_screen.dart:122 (`if (ok) await repo.remove(p.id);`), has no try/catch, so there is no toast either. The error is unhandled and the state is half-changed until the next unrelated notify makes the machine vanish while its secrets remain. `pinHostKey` has the same shape and is also wired as a fire-and-forget void callback (app.dart:62 `(fp) => machines.pinHostKey(profile.id, fp)`). A failed write is therefore an unhandled error, the trusted-on-first-use pin is not persisted, and the next launch trusts whatever key it sees. Fix: call `notifyListeners()` from a finally block after the in-memory change, delete the secrets before dropping the profile (or roll back on failure), and have callers catch and show 'Could not remove X. Try again.'

#### P2 (conf 0.55) A 160-char preview row cut can hide the tail of an approval command and still look uncut
`app/lib/data/repositories/pane_previews.dart:528-533`

`previewRows` cuts every row longer than `maxLength` (160) with `_cut`, which does `s.substring(0, end).trimRight()` and leaves no marker. The 'long command, check it all' guard in prompt_detector.dart `_rowCut` only detects a cut heuristically: `row.trim().length > 160 || row.length >= 156`. If the characters just before column 160 are whitespace, `trimRight` shortens the cut row below 156 characters and the guard does not fire. A command padded with spaces (or an agent that is prompt-injected into emitting one) therefore shows only its harmless head. The card, the answer dock, and the notification built by PaneAnswerer/AttentionNotifier then offer a one-tap Allow with no confirm. commandRisk also scores only the visible text. Needs a terminal wider than 160 columns, which is common on a desktop herdr. #### P3 (conf 0.4) herdr API errors in the connect loop are always 'retry', so a rejected subscription flaps the machine with a raw code

## Round 2: keeper script, first half
#### P2 (conf 0.7) scan() marks a starting keeper exited after 16 list probes, and kill then orphans it
`app/lib/data/services/keeper_script.dart:366-368`

The keeper only registers its listener after the agent answers `initialize` (`self.update_reg(self.listener)` in `on_init_response`). Until then nothing calls `accept()`. Every `list` runs `sock_alive()`, which connects and closes. Each probe stays in the kernel's accept queue, which `listen(16)` caps. Once the queue is full, `connect` fails (ECONNREFUSED on macOS, a 2 s timeout on Linux). `scan()` then calls `mark_stale()`, which writes `state: exited` ('The keeper process is gone') and unlinks the live keeper's `.sock`. A cold `npx -y` start can take up to 120 s, and the app lists every 30 s plus on resume and pull-to-refresh. Attach retries open more connections in the same queue. The next `kill` sees `state == exited`, skips the SIGTERM, and only deletes the files. The keeper and agent keep running with no record and no socket. `cmd_attach` has the same flaw: its `mark_stale` fires on any connect failure without checking that the pid is dead. Trigger probability is low (16 probes or attaches in one start window). The effect is an unreachable, unkillable process. Repro: throwaway home, fake agent that never answers initialize. `start` it, then run `list` 20 times. Output: probes 1-16 report state 'starting'; probes 17-20 report 'exited'. The record then reads 'exit_reason: The keeper process is gone (killed, or the host restarted).' and the keeper pid is still alive. `kill <id>` printed {"ok":true}, the files were gone, and pid 44238 plus the agent were still running (I killed them myself afterwards). Separately, a bare unix listener with `listen(16)` that never accepts: probe 17 gets ConnectionRefusedError on macOS. Fix: in `scan()`, skip `sock_alive` while `state == 'starting'` and the pid is alive, and make `cmd_attach` check `pid_alive` before `mark_stale`.

#### P2 (conf 0.9) Every agent and its tools inherit the keeper's umask 077
`app/lib/data/services/keeper_script.dart:2396-2396`

`daemon()` calls `os.umask(0o077)`, and `spawn()` then starts the agent with `preexec_fn=_default_signals`, which only resets three signals. The agent and everything it runs (git, build tools, editors, shell commands) therefore create files 0600 and directories 0700, even though the SSH login that started it had umask 022. In shared folders, docker bind mounts, web docroots, or group-shared repos, files the agent writes are unreadable by the web server or teammates, which is a behaviour difference from a terminal session. The 077 umask is meant for the keeper's own record, socket and log files only. Repro: throwaway home, fake agent that records `os.umask()` and creates a file. With the shell umask at 0022, `start` gave agent umask 0o77 and a created file `-rw-------`. Fix: keep the previous value (`LOGIN_UMASK = os.umask(0o077)` in `daemon()`) and restore it in `_default_signals()` with `os.umask(LOGIN_UMASK)`. That function is shared by the agent spawn at line 1040 and the hook spawn at line 1838.

#### P2 (conf 0.8) finish() blocks the event loop for up to 2 s per client that is not reading
`app/lib/data/services/keeper_script.dart:2039-2050`

When the agent exits, `finish()` makes every active connection blocking (`setblocking(True)`, `settimeout(2)`) and calls `sendall(bytes(c.wbuf) + note)`. A client that is not draining its socket (phone asleep, SSH window full, so the attach process is blocked on its own stdout) holds up the keeper for the full 2 s timeout. 16 such clients means about 32 s. Clients are served in set order, so a healthy phone behind stalled ones gets `_herdr/agent_exited` late. Until `self.save()` at the end of `finish()`, the record still says `running`, so `list` and the board show a dead agent as live. The pane cleanup and the `kill` command's 6 s wait are delayed too, and `kill` may escalate to SIGKILL on the keeper. Repro: real keeper with 5 attached clients that never read (including the prompting one). A fake agent streams about 9 MB, then exits with code 3. The `exited` record appeared 10.8 s after the prompt, which is about 5 clients x 2 s plus the flood. Fix: write the final state and record first. Then try a non-blocking `send` of the notice, with one shared deadline for all clients (or skip any client whose `wbuf` is non-empty).

#### P2 (conf 0.45) A silently dead phone connection counts as a live phone and is never reaped
`app/lib/data/services/keeper_script.dart:1229-1240`

Nothing closes an active connection that stays quiet. `tick()` only expires connections that never sent a valid line, and `put()` only drops one on a write error or a 64 MB backlog. The keeper has no way to tell that a phone vanished on a half-open link. sshd's default is `ClientAliveInterval 0` plus 2 h kernel keepalives, so the host-side `attach` process lingers. Such a ghost counts as `clients()`. In `end_turn` (`if any(not c.viewer for c in self.clients())`) it makes the keeper treat the turn end as seen. That clears `unseen_end`, so no `done` hook fires and `unseen_done` stays false, and the user gets no 'agent finished' alert. `info()['clients']` is also wrong. Each phone reconnect during a flaky period adds another ghost. After 16, `accept()` closes every new connection immediately (`if len(self.conns) >= 16: s.close()`), so the phone gets an instant hang-up when it re-attaches. The docs describe seen/alert semantics only in terms of attached clients and do not mention dead-peer detection. I did not reproduce this against sshd; the lingering `attach` is inferred from default sshd settings. Suggested fix: have the keeper send a `_herdr/ping` request to each client every ~30 s and close any client that has sent no line (a JSON-RPC method-not-found reply is enough to count as liveness) within ~90 s.

#### P3 (conf 0.6) nvm directories are ordered by string, so an old node can beat a new one
`app/lib/data/services/keeper_script.dart:206-207`

`search_dirs()` appends `sorted(glob(~/.nvm/versions/node/*/bin), reverse=True)`. That is lexicographic order, not version order. This list is the PATH given to the agent (`env['PATH'] = ':'.join(self.dirs)`) and the place `which('npx')` and the node adapters are resolved. With node v8 or v9 installed next to v18, v20 or v22, string order puts v9 first, so `npx -y @agentclientprotocol/...` and the agent's own `node` run on the old version. It also breaks when v100 arrives (v99 sorts above it). Only affects hosts whose node comes from nvm and is not already earlier on PATH (non-interactive ssh does not source nvm, which is why this code exists). Repro: sorted(['v8.17.0','v9.11.2','v18.19.0','v20.11.1','v22.1.0'], reverse=True) gives v9.11.2, v8.17.0, v22.1.0, v20.11.1, v18.19.0. Fix: use a key that compares the digits as integers, e.g. `key=lambda p: [int(x) for x in re.findall(r'\d+', p.split(os.sep)[-2])]`, with reverse=True.

#### P3 (conf 0.55) Alert redaction misses `curl -u user:pass` and `-pPASSWORD` forms
`app/lib/data/services/keeper_script.dart:400-417`

This is a different gap from the round-1 `Authorization: Token` finding. The summary handed to the on-blocked hook (ntfy and similar third-party services) is the first line of the tool title. #### P3 (conf 0.45) A refused or errored prompt is reported as a finished turn (done alert, unseen_done)
`app/lib/data/services/keeper_script.dart:1799-1805`

`end_turn` takes `stop` from `result.stopReason`. For an error response (expired login, rate limit) that is None. For a refused prompt (-32003) the code does retract and then falls through to the common tail. With no non-viewer client attached, the tail sets `self.unseen_end = {'stop': None}` and runs `hook('done', 'Turn finished')`. The user is told a turn finished when it errored, and `unseen_done` becomes true for a session that is mid-turn (refused means another turn is running). #### P3 (conf 0.3) Alert hook can fail to start under python 3.6 with an ASCII filesystem encoding
`app/lib/data/services/keeper_script.dart:1810-1825`

The module header promises python 3.6+. `trunc()` appends U+2026 when it cuts, and the summary or title can hold any non-ASCII text (typographic quotes, CJK or cyrillic paths in a command). `hook()` puts them into `env['KEEPER_SUMMARY']` and `env['KEEPER_TITLE']` for `subprocess.Popen`. #### P1 (conf 0.9) commandRisk's git-options regex backtracks exponentially and freezes the UI on `git -C -C -C ...`
`app/lib/data/repositories/command_risk.dart:65-66`

Fix: make the alternatives mutually exclusive, e.g. generic flag `(?!-[Cc]\s)(?!--(?:git-dir|work-tree|namespace)\s)-{1,2}[\w-]+(?:=\S+)?`, and/or cap the length of text passed to the rules.

## Round 2: keeper script, second half and installer
#### P1 (conf 0.88) Command wrapper breaks under fish and csh login shells, contradicting the docs
`app/lib/data/services/keeper_command.dart:101-106`

`_wrap` builds `sh -c "$(echo B64 | { base64 -d 2>/dev/null || base64 -D; })"`. The comment here and the claim in `docs/ARCHITECTURE.md:218-221` say this lets any login shell (fish, csh) pass the command through unchanged. But sshd hands the whole string to the user's login shell (`$SHELL -c '<cmd>'`), and that shell parses the `$( )` and `{ ...; }` itself before `sh` ever runs. Throwaway repro with the exact command shape on this machine: `fish -c "sh -c \"$(echo ZWNo... | { base64 -d 2>/dev/null || base64 -D; })\""` exits 127 with `fish: '{ ... }' is not supported for grouping commands. Please use 'begin; ...; end'`. `csh -c` and `tcsh -c` exit 1 with `Illegal variable name.`. zsh and dash work. For a user whose login shell is fish or csh, every keeper command fails (list, start, attach, install, follow). The app reports it as the fatal 'The machine could not run the command (command not found)' (`_failure` maps 126/127 to fatal). `bridge_command.dart:330-333` has the same copy, so the herdr mux also fails for those users. Fix: make the outer word a single-quoted `sh -c` whose body holds the `$( )` and braces, for example `sh -c 'exec sh -c "$(echo B64 | { base64 -d 2>/dev/null || base64 -D; })"'`. Base64 has no quote or `!` characters, and single quotes are literal in fish, csh and posix shells. Then add a test that runs the produced command under fish and csh when they are installed.

#### P2 (conf 0.8) A NUL byte in an agent-supplied title or question silently drops the blocked alert
`app/lib/data/services/keeper_script.dart:1826-1841`

`hook()` puts `redact_line(text)` and `redact_line(self.title)` into the child environment. `redact_line` splits on line breaks, collapses whitespace and masks secrets, but it leaves control characters such as NUL (`\u0000`) in place. `subprocess.Popen(env=...)` raises `ValueError: embedded null byte` for such a value. The surrounding `except Exception` only calls `dlog('alert hook failed to start')` and returns. Repro: in an e2e run with the fake agent, a prompt `perm:rm -rf ~\u0000 # build` reached the client as a held permission request. The hook file never ran (`hook.out` empty). The keeper log said `alert hook failed to start: embedded null byte`. The title and question text are controlled by the agent, and so by anything that prompt-injects it. A tool title with a NUL therefore turns off the push alert for a dangerous request that still waits on the phone, which contradicts 'Attention is the product'. The same text also reaches the hook with raw ESC and other C0 bytes. Fix: strip `[\x00-\x1f\x7f-\x9f]` in `redact_line` (after the first non-empty line is taken) so the value is always a valid env string. Optionally retry once with a sanitised summary.

#### P2 (conf 0.55) A silently vanished phone's attach never times out, so the done alert and unseen-done badge are suppressed and the 16-connection cap fills
`app/lib/data/services/keeper_script.dart:1801-1805`

An attach that the phone abandoned without a FIN/RST (radio loss, NAT drop; `keepAliveInterval` is null in `ssh_transport.dart:253`) stays an `active`, `live` connection in the keeper. `tick` only reaps connections that never sent a line (`not ch.active and t - ch.born > 30`), and nothing pings active ones. `end_turn` then sees a non-viewer in `self.clients()`, so it sets `unseen_end = None` and returns. It also skips the `done` hook, because `any(c.active and not c.viewer ...)` is true. Repro (e2e): client A initialises, creates a session and sends `plain`, then goes silent without closing; the turn ends. `hook.out` stayed empty and `list` showed `unseen_done:false`. Nobody is told that a turn finished while the person's phone is dead. The ghost persists until the attach process dies. That takes the TCP retransmit timeout after the next output, or, for an idle session, sshd's keepalive, which is off with the default `ClientAliveInterval 0` and roughly 2 h with kernel keepalive. Ghosts also pile up toward `len(self.conns) >= 16`, after which `accept()` closes new attaches immediately. Reconnecting on flaky radio can therefore lock the person out. Fix options: have the attach or keeper send a periodic heartbeat or ping and drop a connection that does not answer within N seconds. Or count a connection toward 'phone attached' only if it spoke in the last N minutes. Or cap by closing the oldest connection of the same label instead of the newcomer.

## Round 2: performance
#### P1 (conf 0.7) Risk regexes backtrack exponentially/quadratically on agent text, on the UI isolate
`app/lib/data/repositories/command_risk.dart:47-70`

`commandRisk`, `_first` and the `_git` prefix (`-[Cc]\s+\S+` vs `-{1,2}[\w-]+`) are ambiguous when an option's argument itself starts with `-`. `git -C -C -C ...` can be consumed as flag-then-flag or flag-takes-flag, which gives Fibonacci-many parses before the `\s+push` failure is reported. Every rule of the form `\b<word>\b[^;&|]*<tail>` (find, docker, gcloud|az, aws, alembic.., curl, dd, git reset/checkout/branch..) is also O(occurrences x length). `_riskCharLimit` lets 200,000 chars through, up to three readings per request (command, the joined fields, each command-like field), and this is synchronous in `describePermission`. Reachable inputs: an ACP permission `command`; a terminal row shown as a prompt (`prompt_detector.dart:248`, run again on every preview read of a blocked pane, rows up to 160 chars). Repro (Dart VM JIT on the real `command_risk.dart`): `git ` + `-C `x24 (77 chars) took 682 ms; x28 (89 chars) took 4.95 s; x30 (95 chars) took 14.1 s; each extra `-C ` multiplies the time by ~2.9, so a 160-char row never returns. A 32 KB `cat <<EOF` prose heredoc containing docker/az/aws/find/kubectl/git every 63 chars took 1.1 s. 32 KB of `echo find lorem ipsum ` took 404 ms. A bare `\bfind\b[^;&|]*\s-delete\b` on 50 KB took 1.6 s, 4x per 2x length, so about 25 s at the 200 KB cap. AOT release builds run Dart regexes in the bytecode interpreter, so a phone should be slower still (unmeasured). Effect: frozen UI and ANR at the exact moment the app shows an approval, and a restart loop if the pane preview re-runs the detector. `terminal_links.dart` already documents this hazard (hand-written scanner 'prone to catastrophic backtracking on hostile output'); `command_risk.dart` does not follow it. Fix: (1) make the git option alternatives disjoint, e.g. `-[Cc]\s+(?!-)\S+` and `--(?:git-dir|work-tree|namespace)(?:\s+|=)(?!-)\S+`; (2) bound every `[^;&|]*` span, e.g. `[^;&|]{0,400}`; (3) lower the judged limit to a few KB and treat anything longer as 'too long to judge' (a reason shown to the person) instead of silently unjudged; (4) add a test that runs `commandRisk` on `git -C -C ... x` and on a 100 KB find-heavy string under a time budget.

#### P2 (conf 0.6) Reattach decodes and folds the whole held prefix (up to 4000 lines / 1 MiB) in one task
`app/lib/data/acp/acp_client.dart:676-686`

On `_herdr/replay`, `_onReplayFrom` runs `_update(sid, (_) => foldLines(sid, since.prefix))`. `foldLines` does `jsonDecode` + `SessionUpdate.parse` + `state.apply` for every line before the stamped turn, with no slicing and no yield. The prefix is everything the phone already holds. It is bounded only by the recorder caps (4000 lines, 1 MiB, `TranscriptRecorder`), and the held `_state` is the very state that fold recomputes. Trigger: any reattach of a long session after a radio drop, which the app treats as normal. The live replay is carefully sliced (`_WorkerExec._maxLines = 256`; its comment says a 2048-line / 256 KB batch cost 5-10 ms of JSON and 20-40 ms of reducer on a mid-range phone and dropped frames at every attach). This path hands the UI isolate roughly 4x that in a single task: about 4000 lines, ~20-40 ms JSON plus ~40-80 ms reducer, scaled from that comment, i.e. several dropped frames, unmeasured. A related cost in the same attach: `linesBefore` (`transcript_log.dart:86`, via `_keepOlderLines` at `acp_agent_session.dart:843`) decodes and folds the older lines again when `withHeld` kept older items, plus builds `signaturesOf` over both lists. Fix: the held state already is the fold of the prefix. Remember it (state at the cut) when the stamp is read, or fold in a worker isolate, or at least fold in 256-line slices with a frame yield between them. Record the line index per item so `linesBefore` needs no refold.

#### P2 (conf 0.55) Opening a cached session folds ≤4000 updates synchronously, then JSON-re-encodes them all
`app/lib/data/acp/transcript_log.dart:61-78`

`acquire()` calls `_showCached`, which reads the cache in an isolate and then runs `replayCachedTranscript(cached)` on the UI isolate: a loop of `applyUpdateParams` over up to 4000 updates (the recorder cap) in one task, with no yield. When the session then attaches while holding that state, `heldLines` is `cachedLines(_cachedCopy!)` (`acp_agent_session.dart:782-785`): `jsonEncode` of every cached update, up to ~1 MiB, on the UI isolate while the screen is animating in. The isolate had the raw rows (`readTranscriptFile`) and threw them away. The order is fold, re-encode, then the full re-decode and fold of finding 2. The same data is processed three times on the UI thread per open. Estimate (unmeasured, scaled from the `isolate_transport.dart` comment): tens of ms to ~100+ ms in one task. `PreconnectTap` and `preload` also trigger `acquire`/warm on a finger-down, so this lands at the moment the 'instant' budget matters most. Fix: return the raw `lines` in `CachedTranscript` and use them for `heldLines`. Do the fold in the worker or in time-budgeted slices, as `ObservedAgentSession._applyBatch` does (6 ms budget).

#### P2 (conf 0.5) A finished message is re-parsed in full: the settledAt copy misses the segment memo
`app/lib/ui/features/agent_session/transcript_plan.dart:333-338`

`segmentsOf` memoises per message object (`_settled = Expando`, keyed on identity). When a streaming message ends, `session_state.dart:754` replaces it with `m.settledAt(now)` (line 123), which builds a NEW `TranscriptMessage`. The next `_replan` therefore calls `parseMd(...)` over the entire text synchronously on the UI isolate (`transcript_plan.dart:570`), although `LiveMessageModel.md` (`StreamingMd`) has just parsed every block of the same text chunk by chunk. Trigger: every long agent answer, in the frame it ends or when the next tool call starts. `markdown_view.dart:15` states 200 KB parses in about 70 ms on a desktop, so about 0.35 ms per KB. A 20 KB answer is about 7 ms desktop and a 100 KB answer about 35 ms, a likely hitch on a phone (unmeasured). While a message is live, `_segments(head)` also re-parses the committed head blocks on every replan (no memo). Fix: when the live row settles, seed `_settled[settled]` from the model's `md.frozen` plus the unhealed tail (the StreamingMd invariant already guarantees equality with `parseMd`). Alternatively carry the memo across `settledAt`, e.g. key it on the `LiveText`/`blocks` list identity, and memoise `_segments(head)` per live message.

#### P2 (conf 0.5) Unwatched attached sessions schedule a vsync frame for every streaming burst
`app/lib/data/repositories/acp_agent_session.dart:1851-1863`

`boot.dart:119` injects `FrameFlush`. In `_changed`, a non-quiet session always uses `_flush.nextFrame(_flushDue)`, which is `binding.scheduleFrameCallback`. That requests a full frame (BeginFrame/drawFrame/compositeFrame) at up to 60 Hz while text streams. The repository keeps up to `maxAttached` = 4 sessions attached per machine (blocked ones plus 3 recent) with no screen holding them, and any of them streaming drives this path while the person is on the board or another screen. The flush only serves a watching row (`live.flush()`) and listeners that gate on a signature (`_onSession`), so in that case every frame is an empty wake-up. This contradicts 'nothing moves at rest' and 'every timer... is a cost to the person' (AGENTS.md principles 1 and 8). It is a battery and radio-adjacent CPU cost, not a correctness bug. Unmeasured. Fix: use `nextFrame` only while the session is held (`_holds > 0 || _warms > 0`). Otherwise `_flush.after(notifyEvery or ~250 ms, _flushDue)`; urgent changes (phase, request, link) can keep `nextFrame`.

#### P2 (conf 0.5) Session overview re-runs the whole permission risk analysis on every rebuild just to get a title
`app/lib/ui/features/agent_session/session_overview.dart:406-409`

`_pendingText` calls `describePermission(request).title` for up to 3 pending requests inside `SessionSelect.builder`. `describePermission` does far more than the title: `_commandTexts`, `_cap(_foldBlankRuns(visibleText(raw)))`, `commandRisk` over up to 200,000 chars per reading (see the regex finding), `riskOf(title)`, and `pathRisk` per whitespace token of the title. The sheet rebuilds whenever `state.items`, `plan`, `pending`, `usage` and similar lists are replaced, which is every tool update of a running turn, and on each toggle. The dock correctly caches its result in `late final _info`; the overview does not. Cost per rebuild is O(pending x command size x number of rules); with a long command in the first 3 requests it repeats the multi-ms to multi-second regex work for nothing. Fix: `_pendingText` should call `permissionTitle(request)` + `visibleText`. The title does not need `describePermission`. Otherwise memoise `describePermission` per `PermissionRequest` in an Expando.

#### P3 (conf 0.55) Scrollback at its row cap defeats the append-only fast path, so every read walks all 20,000 rows
`app/lib/ui/features/pane/scrollback_history.dart:361-386`

`ScrollbackHistory` exposes `RowsSnapshot(_history, ...)` and `TerminalDocument.update` skips the history only while `identical(list, _historyList)`. At `maxRows` = 20000 (or 8M code units), each read that scrolls new rows in calls `_enforceCap`, which does `_detach()` (a 20,000-element copy because a snapshot is out) and `removeRange(0, count)`. The snapshot after that has a new backing list on every read, so `known` is 0 and `TerminalDocument.update` re-walks and re-compares every line (`lines.removeRange`, the `candidate.src == raw` loop, the `historyColumns` max loop) on each read. A pane that streams output reaches the cap quickly (40 new rows per 120 ms read gives 20,000 rows in ~1 minute). Repro (throwaway Dart on the real `ScrollbackHistory` + `TerminalDocument`, parser stubbed): 399 of 399 steps after the cap produced a new backing list; `doc.update` averaged 27 µs at 4k-12k rows of history and 313 µs at the cap, about 11x worse. That is small on a desktop, probably 1-3 ms per read at ~8 Hz on a phone (unmeasured), and then it never recovers. It also makes the doc comments ('an update is proportional to what changed', 'a snapshot's list is only appended to') untrue once the cap is hit. Fix: trim the top in chunks (e.g. drop 1000+ rows when 20000 is exceeded so most reads stay append-only), or let `RowsSnapshot` carry a `start` offset into the same backing list so dropping from the front keeps the identity. Add a test with `maxRows` small that asserts the backing list identity survives a read at the cap.

#### P3 (conf 0.45) Pretty-printing a large JSON file still joins, re-encodes, re-decodes and splits it on the UI isolate
`app/lib/ui/features/files/file_viewer_view_model.dart:388-396`

`formatJson` offloads only decode/encode, and only above 128 KB. After that, `doc.text` joins every loaded line (up to the 5 MB viewer limit) on the UI isolate. The formatted string is then `utf8.encode`d and handed to `TextDocument.append`, which decodes it again, runs `split('\n')`, allocates a String per line and measures each line. A minified 5 MB JSON file expands to several MB and hundreds of thousands of short lines, so these are about five passes and ~500k allocations in one task. Below 128 KB the whole job runs synchronously (`SynchronousFuture`). Estimate: likely hundreds of ms for the manual 5 MB case, tens of ms for the auto-trigger case (unmeasured). Fix: do join, format, utf8 split and line-offset indexing in the isolate and return the lines (or the bytes plus line starts). Add a `TextDocument.fromLines`/adopt constructor that skips the encode/decode round trip.

#### P3 (conf 0.35) Markdown files under 50,000 chars are parsed on the UI isolate, by the file's own cost figure
`app/lib/ui/features/files/markdown_view.dart:15-72`

`_parseOffThreadFrom = 50000`. The file's comment says a 200 KB message parses in ~70 ms on a desktop, so a 49,999-char README is ~17 ms on a desktop and plausibly 50-80 ms on a phone (3-5x, unmeasured) as a synchronous parse inside `didUpdateWidget`/`initState`. It runs on open, on 'Load more' and on every refresh that changes `document.bytes`. `doc.text` (a line join) is also built on the UI isolate each time. Fix: lower the threshold to a few thousand chars, or always `Isolate.run` the parse (the result returns by exit with no copy), showing the previous parse until it lands.

#### P3 (conf 0.35) The live message row mounts every frozen block eagerly in one non-lazy Column
`app/lib/ui/features/agent_session/live_message_row.dart:104-143`

The transcript is a lazy SliverList, but `LiveMessageRow._frozen` keeps all frozen blocks of the arriving message as built widgets in one `Column` (`List.of(_frozenRows)`), so a 140 KB answer (the figure the docs use) holds roughly hundreds of mounted paragraph render objects. Whenever the row is built from scratch for a message that already has text, all blocks build, lay out and paint in one frame: scrolling back down to the live message, the plan pulling the live row back in, or opening a session mid-stream. Each freeze also re-creates the Column widget and re-walks N children, which is O(N) per freeze and O(N²) over a message. The memory of every laid-out paragraph stays resident. Unmeasured; a typical 2-10 KB answer is fine, a very long streamed answer is not. Fix: promote older frozen blocks into plan rows (the live PlanRow already carries `firstBlock`, so keys line up) or chunk frozen blocks into K-block rows so they live in the lazy list.

#### P3 (conf 0.35) Subagent log fold yields every 150 lines regardless of how big those lines are
`app/lib/data/repositories/subagent_transcripts.dart:300-312`

`SubagentLogReader.poll` decodes (`utf8.decode` + `jsonDecode` in `_mapper.map`) and reduces each line, yielding with `Future.delayed(Duration.zero)` only every `sliceLines` = 150 lines. `maxLineBytes` allows a single log line of up to 256 KB (tool results) and `maxReadBytes` is 1 MiB, so one 150-line slice can contain several hundred KB to ~1 MB of JSON plus reducer work. Estimated tens of ms per slice on a phone (unmeasured) against a 16 ms frame. `ObservedAgentSession._applyBatch` already slices by a 6 ms `Stopwatch`; this reader does not. Also, when the file grows by more than 1 MiB between ticks, the reader resets and re-parses everything. Fix: add a `Stopwatch` budget next to `sliceLines` and yield when it is spent.

#### P3 (conf 0.3) MachineScreen watches the whole connection at the root and rebuilds under a covering route
`app/lib/ui/features/machines/machine_screen.dart:60-60`

`MachineScreen.build` does `context.watch<MachineConnection>()` and builds every workspace section with non-lazy `_PaneRow`s (up to 30 per workspace). `MachineConnection` notifies about once per 1.5 s (`churnInterval`) while any agent runs. A covered route stays built (`maintainState`), so a pane or session screen on top still pays for rebuilding all rows underneath. The Agents board avoids this with a `TickerMode`-gated cached page; this screen does not. The cost is small per rebuild (tens of rows every 1.5 s, unmeasured) but needless and against 'nothing rebuilds that does not have to'. Fix: return the cached subtree while `TickerMode.of(context)` is false (as the board does), or `select` only the fields this screen shows.

## Round 2: security
#### high (medium) Answer buttons run from the lock screen with no unlock; command text is not hidden there
`app/lib/data/services/local_notifier.dart:61`

Terminal-agent notifications carry up to two answer buttons (Allow/Yes/No...). They are plain broadcast PendingIntents (showsUserInterface unset), and no notification visibility is set. Android runs a broadcast action from a secure lock screen without asking for unlock unless the action opts in (setAuthenticationRequired, API 31+, which flutter_local_notifications 22.3.1 does not expose). Anyone holding the locked phone can read the command and tap Allow. The same buttons also work on the unlocked shade for anyone glancing at it.

#### high (medium) Host-key pin is overwritten blindly, and a respawned transport worker re-trusts any key
`app/lib/data/repositories/machine_repository.dart:178`

The pin is stored by `pinHostKey` with no compare-and-set, and the connection keeps handing the worker the profile it was created with, because the pin is deliberately excluded from `_keyOf` so the connection is not rebuilt. For a machine first pinned during this app run (saved without Test), a respawned worker therefore starts with `_pinned == null`. It accepts whatever key is offered, and `pinHostKey` then overwrites the stored pin. This differs from the round-1 'pin lost when worker isolate replaced': the loss is silent re-trust of a different key, and the persisted pin is replaced, so a MITM becomes the permanent trusted host.

#### medium (medium) Hostile host can exhaust phone memory: mux stream has no line cap and inflate output is unbounded
`app/lib/data/services/mux_client.dart:69`

`muxMessages` buffers a plain line with no newline forever (the buffer doubles). `Z` frames are inflated with `zlib.decode` up to a 64 MiB compressed frame, and `E` frames feed one chunked inflater whose partial line grows without limit. `zippedLines` (keeper attach --z) has the same unbounded inflate plus an O(n^2) `partial + text` concatenation. The 64 MiB `splitLines` cap that round 1 flagged does not apply to these paths. A compromised or hostile host, or a first-connect MITM, sends a few MB of zlib (about 1000:1) or an endless unterminated line. The worker isolate runs out of memory and the app dies. Connections are started at boot and retried, so it repeats on every launch until the machine is removed, and it is also the trigger for the pin-overwrite finding.

#### medium (medium) flutter_secure_storage default resetOnError=true deletes the SSH key on any decrypt failure
`app/lib/data/repositories/machine_repository.dart:45`

`KeychainSecretStore` uses `const FlutterSecureStorage()`, whose Android default is `resetOnError: true`. On any exception while reading an entry (Keystore hiccup, key invalidated by a lock-screen or biometric change, ciphertext restored without its Keystore key) the plugin deletes that entry and retries. The app then sees a null key and reports a fatal 'No private key saved for this machine.' Keys generated on the phone exist nowhere else, so this is silent, permanent loss of the only credential. The three reads run together, so one failure can wipe the key while the others survive. Round 1 flagged Auto Backup; this is a separate data-loss path, and it also fires for ordinary Keystore errors.

#### medium (medium) Heads-up shows only the first row of a multi-line command, with Allow buttons right under it
`app/lib/data/repositories/attention_notifier.dart:523`

For a multi-row subject the collapsed text is `<first row> …`, while the buttons are offered whenever the subject is at most 640 characters and the options are not flagged. The needs-you channel is Importance.high, so Android shows it as a heads-up banner. The banner shows the title, that one row, and the action buttons, and a tap on Allow needs no expansion. The person approves a command whose later rows they never saw. This contradicts principle 3, 'the person sees what they approve'. The in-app dock shows up to three lines and the notification's own expanded view shows everything.

#### medium (high) 'Open sign-in page' opens any https link a server banner contains, for any auth type, without showing the destination
`app/lib/data/services/auth_notice.dart:14`

`approvalUrlFrom` returns the first https URL in any pre-auth banner. `SshTransport` and `MachineConnection.onAuthNotice` never check `profile.auth == SshAuth.none` or the host (login.tailscale.com), and `ApprovalButton` opens the URL without showing it. The panel text is the app's own 'Tailscale needs you to approve this sign-in.' A host that is compromised or MITM'd on first connect, or just an sshd Banner containing a URL (key or password machines), puts a trusted-looking 'Open sign-in page' button in the app's own chrome that opens an arbitrary https page, a ready-made phishing prompt. The auth deadline is also stretched to 5 minutes for such a banner.

#### low (medium) Notification title and agent name come from the pane unsanitised, contrary to the code's own comment
`app/lib/data/repositories/attention_notifier.dart:147`

The field comment says everything a notification shows of a pane passes `visibleText`. Only the question, subject and button labels do. The title (`betterTitle ?? pane.title`, then folder, then agent) and the body's `pane.agent` get only whitespace collapse and a 60-character cut. Pane titles are set by the program running in the pane, so [INFERENCE] an agent or terminal output can choose the most prominent line of the notification, including bidi/control characters, directly above the Allow buttons (for example a title like 'Formatting README' above a command it wants approved).

#### medium (high) ntfy plugin accepts the documented placeholder topic, any 16+ guessable topic, and plaintext http with the bearer token
`tool/plugins/herdr-ntfy/notify.py:28`

On public ntfy.sh the topic is the only secret, but the plugin only checks length (at least 16 characters of [A-Za-z0-9_-]). The install snippet in ALERTS.md writes `NTFY_TOPIC=put-a-long-random-topic-here` (28 characters), which passes, so everyone who copy-pastes it posts to one shared, world-readable topic. The messages carry project and tab names, machine name and a screen line ending in '?'. `herdr-notifications` or `aaaaaaaaaaaaaaaa` pass too. `NTFY_URL` accepts `http://`, so `http://ntfy.sh` sends the topic in clear text (the `public` test looks only at the hostname), and `NTFY_TOKEN` is sent as a bearer header over http. Anyone who learns the topic can also post fake alerts whose tap link opens herdr.

#### low (medium) Pin is a bare fingerprint: a server gaining a preferred host-key type looks like an attack and can only be fixed by blind re-add
`app/lib/data/services/ssh_transport.dart:86`

The pin stores `SHA256:<b64>` with no key type, and the app does not set `SSHAlgorithms.hostkey`, so negotiation follows dartssh2's default order (ed25519, rsa-sha512, rsa-sha256, ecdsa...). A host that had only RSA/ECDSA keys when pinned and later gets an ed25519 host key (OpenSSH package upgrades run `ssh-keygen -A`) now negotiates a different key. Every connection fails fatally with 'Host key changed since it was first trusted', and the only remedy offered is to remove and re-add the machine. A dartssh2 upgrade that reorders the defaults would do the same to every pinned machine at once. The app trains users to re-trust blindly and shows neither fingerprint.

#### low (medium) Saving a machine form opened before the first pin erases the pin
`app/lib/ui/features/machines/machine_form_view_model.dart:243`

The edit form keeps the `existing` profile it was opened with. `_pinFor` returns that profile's pin, and `MachineRepository.save` replaces the stored profile wholesale. If the connection pinned the host key (`pinHostKey`) while the form was open, because the machine was offline or never tested, saving without Test writes a profile with a null pin. The next connect trusts whatever key answers. This differs from the round-1 item about a stale Test result: it needs no Test.

#### low (low) Notification answer binds to a 64-bit FNV digest that is trivially forgeable
`app/lib/data/repositories/pane_answerer.dart:20`

`promptDigest` is two 32-bit FNV-style lanes. Each step is a bijection of the state for a given unit, so a chosen suffix of roughly 8-12 characters can steer both lanes to a target. It is the only link between 'the question the notification showed' and 'the question on screen when the button is pressed'. `crypto` (SHA-256) is already a dependency. Exploiting it needs a process that can redraw the pane and a real approval dialog to receive the keys, so practical risk is low, but the guarantee in the docs ('sends only if still the same question') rests on a non-cryptographic hash.

#### low (medium) Private key is shown in clear and left on the clipboard; no FLAG_SECURE anywhere
`app/lib/ui/features/machines/machine_form_screen.dart:183`

The machine form shows the private key (pasted or generated) in a plain multi-line field. Only passphrase and password are obscured. The paste button reads the clipboard and never clears it, so the key stays there (and in IME clipboard history). The window has no FLAG_SECURE, so the key and every command shown in the app appear in screenshots, screen recordings and the Recents thumbnail. The text-field keyboard hints (autocorrect, suggestions off) do not cover the clipboard.

#### low (low) Agent-controlled image name can contain '..' and '/' and reaches gal's raw File path on Android 10 and below
`app/lib/ui/features/agent_session/content_target.dart:58`

For chat images the file name comes from `contentBaseName(block.uri)`. For an https uri it takes `Uri.pathSegments.last`, which is percent-decoded, so `https://h/..%2F..%2Fa.png` gives `../../a.png`; a uri ending in '/' returns the whole string. `share` sanitises '/' but `saveToGallery` passes `_stem(name)` straight to gal. On API <= 29 (requestLegacyExternalStorage is set) gal builds `new File(Pictures/herdr, name)` and stores it as MediaColumns.DATA, so a malicious agent can steer where the saved image lands. Impact is probably limited to Pictures/DCIM by MediaProvider, so this is hardening, not exploitation.

#### informational (medium) Shared remote files stay in cache in clear until the next share; cancelled or partial copies are not removed
`app/lib/data/services/photo_export.dart:92`

`share`/`shareLarge` write the remote file's contents to `cache/photo_share/<name>` and keep it until the next share ('removed by the next share'). A `shareLarge` cancelled mid-copy leaves a partial file. Remote files can hold secrets, and neither the folder nor the file picker's copies are cleared when the app goes to the background or on exit. The cache is private to the app and outside backups, so the exposure is limited to device compromise or backup tooling.

#### informational (medium) Exported MainActivity accepts the notification plugin's intents from any app, so links bypass the manifest filter
`app/android/app/src/main/AndroidManifest.xml:34`

The manifest filter admits only `herdr://agent`. An explicit intent from another app to the exported activity with action SELECT_NOTIFICATION and a `payload` extra is handled by flutter_local_notifications and reaches `_tapped` → `DeepLinks.follow`, so `herdr://session/...` and `herdr://agents` links can also be injected. A SELECT_FOREGROUND_NOTIFICATION intent with the cancel extra can also dismiss a notification by id. Effect is navigation only: forged answer presses are ignored because `_tapped` accepts only `selectedNotification`, and background presses arrive through the non-exported receiver. That type check is the single control that stops an answer from being forged by another app.

#### low (low) Release job builds with the signing key on disk under mutable action tags and a write token
`.github/workflows/release.yml:19`

`release.yml` restores the keystore to `$RUNNER_TEMP` and writes `key.properties` (store and key password) before `flutter build apk`, so every Gradle plugin script of every Flutter dependency can read the key. Actions are pinned to mutable tags (`@v4`, `@v2`), the job has `contents: write`, and the same password serves the store and the key. A compromised dependency or action could exfiltrate the release key or publish a release.

HIGHEST-VALUE MISSING REGRESSION TESTS (name: scenario):
